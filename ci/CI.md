# CI contract and sub-workflows, reference

> Generated by `corral ci docs` from the contract parser and the sub-workflow registry of this Corral: it says what the tool accepts and does, nothing else. Regenerate it after updating Corral; do not edit it by hand.

## How it fits together

The release pipeline (`.github/workflows/release.yml`, or `.gitlab-ci.yml`) is **the same skeleton in every repository**. What belongs to a project lives in two places that you own:

- **`ci/ci.yml`**, the *contract*: one entry per step (install, lint, test, publish…), each a command, a script, a sub-workflow or an explicit skip.
- **`ci/lib/<name>/`**, the *sub-workflows*: small composite actions copied from Corral’s registry into the repository (a tag always runs the sub-workflows of its own commit; a third-party action is named in one place, pinned by commit SHA).

The pipeline file is **generated** from the contract and carries its fingerprint; edit `ci/ci.yml`, then run `corral ci sync`. If the two disagree, the pipeline’s `integrity` job fails and says which.

| Command | What it does |
| --- | --- |
| `corral ci init` | create `ci/ci.yml` (a proposal per step from the project’s stack, which you accept, replace or skip) and generate the pipeline |
| `corral ci show` | what each step does, per repository |
| `corral ci check` | is the contract valid, and is the pipeline the one generated from it? |
| `corral ci sync` | regenerate the pipeline after editing `ci/ci.yml` (and copy the missing sub-workflows) |
| `corral ci add <name> [step]` | turn a registry sub-workflow on: copy it into `ci/lib/<name>/` and point its step at it |
| `corral ci update` | refresh the copies in `ci/lib/` from the registry (one edited by hand is kept unless `--force`) |
| `corral ci libs` | the registry, with each entry’s step, version and pinned third-party actions |
| `corral ci schema` | the contract grammar, in the terminal |
| `corral ci docs [--out <file>]` | this document |

## `ci/ci.yml`

```yaml
version: 1
steps:
  install:
    run: npm ci
  lint:
    script: ci/scripts/lint.sh
    args: "--strict"
  typecheck:
    skip: no type checker in this project
  audit:
    run: npm audit --audit-level=high
    blocking: false
  sast:
    use: ci/lib/semgrep
```

### Top level

| Key | Required | Value | Meaning |
| --- | --- | --- | --- |
| `version` | yes | the number 1 | Version of the contract format. |
| `environments` | no | mapping channel → GitHub environment (channels: alpha, beta, rc, latest) | Which GitHub environment the `deliver` job runs in, by release channel (default: production for every tag). With `alpha: staging`, `beta: staging`, `rc: staging`, `latest: production`, a prerelease tag delivers with the secrets and variables of the staging environment and a stable tag with those of production. A channel left out takes the `latest` one. |
| `runtimes` | no | list of 1 to 6 runtime versions, like [22, 24] | The versions of the language runtime the verify job runs on (one job per version). Default: the model’s own matrix. Set it to what your dependencies really support, for example the versions of the `engines` field. |
| `dependencies` | no | mapping { branch: <name> } | An intermediary branch for dependency updates (Dependabot). Its pull requests go to that branch instead of the default one, where the verify job is ADVISORY (a failure does not block them), so an update is never stuck on its own incompatibility. A pull request from that branch to the default branch then runs the whole blocking pipeline, repair-by-`fix` included: and is where an incompatibility is corrected before it can reach production. `corral work deps` keeps the branch and that pull request in order. |
| `steps` | yes | mapping step name → how to run it | One entry per step; a step you leave out is simply not run. |

### A step

A step is one of **run | script | use | skip**, plus optional keys:

| Mode | Value | Also allowed | What it does |
| --- | --- | --- | --- |
| `run` | text | - | a shell command written as is into the workflow |
| `script` | relative path, no spaces, no “..” | `args` | a script of the repository (the interpreter is chosen from its extension: .sh .bash .mjs .js .cjs .py .rb .ps1 .pl) |
| `use` | ci/lib/<name> | `with` | a sub-workflow of the local registry (corral ci libs) |
| `skip` | text (the reason is required) | - | the step does not apply, and why |

| Key | Value | Meaning |
| --- | --- | --- |
| `run \| script \| use \| skip` | text | Exactly one of them per step. |
| `args` | text | Arguments of a `script` (only with script). |
| `with` | mapping name: value (text, number or boolean) | Inputs of a `use` sub-workflow (only with use). |
| `env` | mapping NAME: value | Environment of the step; NAME in capitals, single-line text values. |
| `fix` | text | The command that repairs what this step reports (a formatter, `eslint --fix`, a code generator). Only with run or script, only on verify steps. By default the check runs first; if it fails, the fix runs, then the check runs AGAIN, the step passes only if that second check passes, and it warns that the repair exists in the runner only (apply it in your branch: `corral code fix`). |
| `fix-first` | true \| false | Run the fix BEFORE the check (then the check is the proof). For deterministic repairs where the result, not the failure, is what matters. |
| `blocking` | true \| false | A failing step stops the pipeline (default true; false for audit, sbom). |

### The steps

They run in this order. Standard steps are proposed by `corral ci init`; **optional** steps exist only when a project declares them (`corral ci add <name>` does it).

| Step | Stage | Kind | What it checks or does | Blocking by default | Registry entry |
| --- | --- | --- | --- | --- | --- |
| `access` | verify | optional | authenticate to the private git dependencies, before the install | yes | `git-auth` |
| `install` | verify | standard | install the dependencies | yes | - |
| `format` | verify | standard | check the formatting | yes | - |
| `lint` | verify | standard | lint | yes | - |
| `workflows` | verify | optional | the workflow files themselves are valid (actionlint) | yes | `actionlint` |
| `typecheck` | verify | standard | type-check | yes | - |
| `codegen` | verify | optional | generated files are in step with their source (schema, types, clients) | yes | `drizzle-drift` |
| `test` | verify | standard | run the tests | yes | - |
| `db` | verify | optional | check the database (migrations, lint, tests) | yes | `supabase-db` |
| `build` | verify | standard | build | yes | `docker-build` |
| `audit` | verify | standard | audit the dependencies | no | - |
| `sast` | security | standard | static analysis | yes | `semgrep` |
| `secrets` | security | standard | secret scan | yes | `secrets` |
| `sbom` | security | standard | software bill of materials | no | `sbom` |
| `codeql` | security | optional | deep static analysis (data flow) | yes | `codeql` |
| `deps` | security | optional | what a pull request changes in the dependencies (known vulnerabilities, licences) | yes | `dependency-review` |
| `vulns` | security | optional | vulnerabilities, secrets and misconfigurations found in the files | yes | `trivy` |
| `deliver` | deliver | optional | publish the package (replaces the model’s default publication) | yes | `cloudflare-pages`, `cloudflare-workers`, `docker-push-ghcr`, `expo-eas-build`, `expo-eas-update`, `expo-web`, `npm-publish-private`, `publish-github-packages`, `supabase-deploy` |
| `docs` | docs | optional | build the documentation site (published to GitHub Pages after a stable delivery) | yes | `docs-site` |

- **verify** steps run in the `verify` job (once per Node version for Node projects). **security** steps run in their own `security` job, which the delivery waits for; it is not run for Dependabot pull requests. **deliver** runs only on a tag.
- A step that is `skip`ped keeps its reason in the generated file as a comment: a reader sees *why* nothing runs.

### Rules

- A step name must be one of the steps above; any other key is refused. `access`, `workflows`, `db`, `codegen`, `codeql`, `deps`, `vulns`, `deliver` and `docs` are optional: they are never proposed, and exist only when declared (corral ci add <name>).
- `deliver` replaces the model’s publication (npm publish --provenance --access public): use it for a private package, another registry or a deployment. It is generated for GitHub (and Gitea / Forgejo) workflows.
- Untrusted GitHub expressions (event data, branch name, actor, inputs) are refused in run and args: pass them through env.
- The commands are written into .github/workflows/release.yml (or .gitlab-ci.yml); after editing, run corral ci sync, otherwise the pipeline’s integrity check and `corral release doctor` report the difference.

## The sub-workflow registry

Corral ships 21 sub-workflows. `corral ci add <name>` copies one into `ci/lib/<name>/action.yml` (GitHub, Gitea, Forgejo) or `ci/lib/<name>/gitlab.yml` (GitLab) with a header `# corral-ci-lib <name> v<version> sha256:…`:

- a copy **without** the header is your own sub-workflow and is never touched;
- a copy **with** the header and an unchanged body is refreshed by `corral ci update` when the registry moves on;
- a copy whose body you edited is kept (`corral release doctor` warns; `--force` replaces it).

| `actionlint` | `workflows` | github | Workflow files (actionlint) |
| `cloudflare-pages` | `deliver` | github | Cloudflare Pages deployment |

| `codeql` | `codeql` | github | Deep static analysis (CodeQL) |
| `dependency-review` | `deps` | github | Dependency review of a pull request |

| `expo-eas-build` | `deliver` | github | Expo builds for Android and iOS (EAS Build) |
| `expo-eas-update` | `deliver` | github | Expo over-the-air update (EAS Update) |

### `actionlint`, Workflow files (actionlint)

Checks the repository's own workflow files, expressions, shell scripts, action inputs, permissions, with actionlint run from its container image. The workflow generated by Corral is excluded by default (it has its own integrity check).

| Property | Value |
| --- | --- |
| Default step | `workflows` |
| Forges | github |
| Version | v1 |
| Needs | Docker on the runner (ubuntu-latest has it) |
| Third-party actions (pinned by SHA) | none |
| Container images | `rhysd/actionlint:1.7.12` |
| Extra token permissions | none |

| Input (`with:`) | Default | Meaning |
| --- | --- | --- |
| `exclude` | `release\.yml$` | regular expression of files to skip (default release\.yml$) |

Example:

```yaml

  install:
    run: npm ci
  workflows:
    use: ci/lib/actionlint
    with:
      exclude: "release\\.yml$|legacy-.*\\.yml$"
```

### `cloudflare-pages`, Cloudflare Pages deployment

### `git-auth`, Read access to private git dependencies

Lets `npm ci` fetch the private repositories your package.json depends on (git+https://github.com/<org>/<repo>.git). Without it the runner has no right to read them and npm falls back to ssh: "Permission denied (publickey)". The token (a fine-grained personal access token or a GitHub App token with read access to the contents of those repositories) is passed as `with: token: ${{ secrets.ORG_READ_TOKEN }}`; it is masked, kept out of the checkout and used only through git's URL rewriting, ssh and https forms included. Fails early, with the fix, when the token is missing or cannot read the dependencies.

| Property | Value |
| --- | --- |
| Default step | `access` |
| Forges | github |
| Version | v1 |
| Needs | a secret holding the token (corral vault publish github), declared with `with: token` |
| Third-party actions (pinned by SHA) | none |
| Container images | none |
| Extra token permissions | none |

| Input (`with:`) | Default | Meaning |
| --- | --- | --- |
| `token` | - | token with read access to the private repositories: pass it as ${{ secrets.NAME }} |
| `host` | `github.com` | git host (default github.com) |
| `check` | - | owner/repo list (space separated) to probe with the token before the install, optional: reads the repositories your package.json names when empty |

Example:

```yaml
version: 1
steps:
  access:
    use: ci/lib/git-auth
    with:
      token: "${{ secrets.ORG_READ_TOKEN }}"
  install:
    run: npm ci
```

### `npm-publish-private`, Private npm publication (npmjs)

Publishes the package as a PRIVATE (restricted) package on npmjs, without provenance (npm only attests public packages). Refuses to publish if a secret-looking file (.env, key, supabase/.temp) is in the tarball, and does nothing when the version is already published. Authentication: trusted publishing (nothing to store) once the package has a trusted publisher on npmjs, otherwise an automation token passed as `with: token: ${{ secrets.NPM_TOKEN }}`.

| Property | Value |
| --- | --- |
| Default step | `deliver` |
| Forges | github |
| Version | v1 |
| Needs | npm >= 11.5.1 for trusted publishing (the model installs it), the registry token as a secret when not using trusted publishing |
| Third-party actions (pinned by SHA) | none |
| Container images | none |
| Extra token permissions | none |

| Input (`with:`) | Default | Meaning |
| --- | --- | --- |
| `access` | `restricted` | restricted (default) or public |
| `registry` | `https://registry.npmjs.org/` | registry URL |
| `token` | - | registry token: pass it as ${{ secrets.NAME }}; empty uses trusted publishing on npmjs |
| `tag` | - | dist-tag (default: the channel of the tag) |
| `forbid` | `(^\|/)\.env($\|\.)\|\.(pem\|key\|p12\|pfx)$\|(^\|/)supabase/(\.temp\|\.branches)/\|(^\|/)\.git/\|(^\|/)node_modules/` | regular expression of paths that must never be published (default: .env files, keys, supabase/.temp, .git, node_modules) |

Example:

```yaml
version: 1
steps:
  install:
    run: npm ci
  deliver:
    use: ci/lib/npm-publish-private
    with:
      token: "${{ secrets.NPM_TOKEN }}"
```

## Recipes

### A public npm package (the model’s own delivery)

Nothing to declare for the delivery: the model publishes with provenance, `--access public`, through trusted publishing. Add the scanners you want.

```yaml
version: 1
steps:
  install:
    run: npm ci
  lint:
    run: npm run lint
  typecheck:
    run: npm run typecheck
  test:
    run: npm test
  audit:
    run: npm audit --json
    blocking: false
  sast:
    use: ci/lib/semgrep
  secrets:
    use: ci/lib/secrets
  deps:
    use: ci/lib/dependency-review
```

### A PRIVATE npm package on npmjs

The model’s `--access public --provenance` would be wrong for a private package. `deliver` replaces it: restricted access, no provenance, a refusal if the tarball holds a secret-looking file. Authenticate with trusted publishing, or give a token as shown.

```yaml
version: 1
steps:
  install:
    run: npm ci
  lint:
    run: npm run lint
  test:
    run: npm test
  sast:
    use: ci/lib/semgrep
  secrets:
    use: ci/lib/secrets
  deliver:
    use: ci/lib/npm-publish-private
    with:
      access: restricted
      token: "${{ secrets.NPM_TOKEN }}"
```

### A private package on GitHub Packages (no secret to create)

### Private git dependencies (`@org/lib` read from other private repositories)

When `package.json` names another private repository (`git+https://github.com/<org>/<repo>.git#main`), the runner has no right to read it: npm falls back to ssh and fails with `Permission denied (publickey)`. The optional `access` step runs before EVERY install (the verify job and the delivery job) and gives git the token, for https, ssh and scp-like spellings alike; it also probes each repository package.json names, so a token that is too narrow fails there, with the repository named, instead of in the middle of npm. Create a fine-grained token with Contents: read on those repositories, store it (`corral vault publish github`) and pass it as a secret. `runtimes` pins the Node versions the verify job runs on.

```yaml
version: 1
runtimes: [22]
steps:
  access:
    use: ci/lib/git-auth
    with:
      token: "${{ secrets.ORG_READ_TOKEN }}"
  install:
    run: npm ci
  typecheck:
    run: npm run typecheck
  test:
    run: npm test
  secrets:
    use: ci/lib/secrets
```

### Deliver to staging for a prerelease tag and to production for a stable one

The `deliver` job runs in the GitHub environment chosen by the tag: `v1.4.0-rc.1` in `staging`, `v1.4.0` in `production`. Each environment holds its own secrets and variables (`corral vault publish github --env staging`, then `--env prod`), so the same step reaches the right Supabase project. Here SUPABASE_ACCESS_TOKEN and SUPABASE_DB_PASSWORD are environment secrets and SUPABASE_PROJECT_REF an environment variable.

```yaml
version: 1
environments:
  alpha: staging
  beta: staging
  rc: staging
  latest: production
steps:
  install:
    run: npm ci
  test:
    run: npm test
  secrets:
    use: ci/lib/secrets
  deliver:
    use: ci/lib/supabase-deploy
    with:
      project-ref: "${{ vars.SUPABASE_PROJECT_REF }}"
      access-token: "${{ secrets.SUPABASE_ACCESS_TOKEN }}"
      db-password: "${{ secrets.SUPABASE_DB_PASSWORD }}"
```

## When something is wrong

| What you see | Why | What to do |
| --- | --- | --- |
| `integrity` job fails: “ci/ci.yml changed since release.yml was generated” | the contract was edited without regenerating the pipeline | `corral ci sync`, commit both files |
| `integrity` job fails: “release.yml was edited” | the generated file was changed by hand or by a bot (Dependabot) | `corral release doctor --fix` restores it through a pull request |
| `corral ci check`: “ci/lib/<name>/action.yml missing” | the contract uses a sub-workflow that is not in the repository | `corral ci sync` copies it |
| `corral release doctor`: sub-workflow “edited by hand” | its body differs from the registry | keep it (it is yours now) or `corral ci update --force` |
| `npm ci` fails: “Permission denied (publickey)” on `ssh://git@github.com/<org>/<repo>.git` | a private git dependency the runner cannot read: npm tried https, then ssh | declare `access: { use: ci/lib/git-auth, with: { token: ${{ secrets.ORG_READ_TOKEN }} } }` (`corral ci add git-auth`) with a token that can read those repositories |
| `git-auth`: “the token cannot read github.com/<org>/<repo>” | a fine-grained token needs the repository selected and Contents: read; a classic one needs the repo scope | widen the token, store it again with `corral vault publish github` |
| `corral ci add` refuses on GitLab | the entry exists for GitHub-style workflows only | write your own `ci/lib/<name>/gitlab.yml` (a file without the header is never touched) |
| a `with:` value with `${{ … }}` is refused in `run`/`args` | untrusted expressions must not be pasted into a command | pass them through `env:` |
